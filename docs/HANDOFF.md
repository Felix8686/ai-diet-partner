## 当前产品边界

继续严格遵守 `AGENTS.md` 与 `docs/PRODUCT.md`：

- MVP 只做饮食管理。
- 前五个大版本禁止加入吉祥物、卡通 IP、拟人角色。
- 不加入喝水、步数、久坐、运动打卡、训练计划等泛健康功能。
- 不做卡路里流水账，不做冰箱库存管理。
- 外卖、食堂、便利店、自己带饭、外食都是正常饮食环境。
- 避免“未达标、还差多少、预计减重”等考核式表达。
- AI/系统的价值是理解用户为什么没执行，并让下一次方案更容易执行；不要为了体现“伙伴感”增加无意义文案。
- 未经明确任务不得扩展地图、美团/高德、MCP、外部 Agent、真实 AI Provider。

## 下一阶段任务

### Round 04：让“每日反馈”真正改变下一周方案 v0

这一轮只做**本地、确定性、可解释的反馈调整闭环**。

目标不是接 AI，而是证明产品最核心的差异化逻辑：

> 用户没执行 → 系统理解失败原因 → 下一周方案主动降低相同失败再次发生的概率。

Hermes 开始前必须：

1. 拉取最新 `main`。
2. 从最新 `main` 新建独立分支：`hermes/round-04`。
3. 禁止直接修改、commit 或 push `main`。
4. 完成后创建 PR 指向 `main`，不得自行合并。

### A. 先把本地数据层升级为“按周保存”

当前只有单个当前周方案/采购清单。Round 04 需要同时保留本周和下周，因此做最小迁移：

- 周方案按 `weekStart` 保存。
- 采购清单按 `weekStart` 保存。
- 每日反馈继续按本地日期保存。
- 旧版单周 localStorage 数据必须有兼容迁移或安全回退，不能让已有用户打开后直接丢数据或崩溃。
- 不做完整历史中心，不做云同步。

建议提供简单接口，例如：

- `loadWeeklyPlan(weekStart)`
- `saveWeeklyPlan(plan)`
- `loadShoppingList(weekStart)`
- `saveShoppingList(weekStart, items)`
- `loadFeedbackForWeek(weekStart)`

具体命名可调整，但不要过度抽象。

### B. 建立可测试的反馈聚合层

新增一个纯函数层，把一周反馈转换为少量、明确的调整信号。

至少处理当前已有原因：

- `没时间`
- `太麻烦`
- `买不到`
- `太贵`
- `不喜欢`
- `临时聚餐`
- `其他`

v0 规则：

1. **没时间**
   - 下一周提高快速餐、免烹饪、便利店/食堂等低时间成本方案权重。
   - 对高准备时间模板增加明显惩罚。

2. **太麻烦**
   - 下一周降低需要多种厨房能力或较长准备时间的模板权重。
   - 优先一锅、免烹饪、简单组合类模板。

3. **买不到**
   - 下一周优先当前模板池中采购更简单、常见、便利店/食堂可获得的方案。
   - 不要发明真实商店库存数据。

4. **太贵**
   - 下一周增强成本惩罚，在不违反其他硬约束时优先更便宜方案。
   - 不修改用户原始预算字段。

5. **不喜欢**
   - 当前反馈不是餐别级评价，不能武断永久拉黑某种食材。
   - v0 只降低该反馈日期当天主餐模板在下一周再次出现的概率，不写入永久 dislikedFoods。

6. **临时聚餐**
   - 视为偶发外部事件，不因为一次聚餐就改变整个饮食偏好。
   - 可记录，但默认不形成负向调整信号。

7. **其他**
   - 保留数据，但 v0 不做自由文本 NLP。

必须保证：

- 没有反馈时，下周仍使用正常 planner，不制造虚假调整。
- 少量单次反馈不要导致整周方案剧烈变化。
- 相同 profile + 相同反馈 + 相同 weekStart 的结果保持稳定，不使用 `Math.random()`。

### C. 把调整信号接入规划器

不要复制第二套 planner。

在现有 `generateWeekPlan()` 周围增加一个轻量可组合机制，例如可选 `adjustments` 参数或等价方式。

硬约束优先级不能改变：

1. 饮食禁忌 / 过敏
2. 厨房能力
3. 做饭时间硬上限
4. “通常不做饭”等明确现实限制
5. 预算不可静默突破
6. 然后才是反馈形成的偏好调整

反馈绝不能绕过过敏、纯素、厨房能力等硬约束。

### D. 增加“下周方案”最小用户路径

在 `/week` 做一个轻量入口，不要重做页面：

- 用户可以从本周方案进入“看看下周怎么调整”或同等自然表达。
- 生成下一周方案时读取本周每日反馈并应用调整信号。
- 生成结果按下周 `weekStart` 单独保存，不覆盖本周方案。
- 用户可以在本周 / 下周之间查看，但不要建设复杂日历或历史中心。
- 下周采购清单必须独立于本周采购清单，不能生成下周后把本周已买状态覆盖掉。

如果本周没有任何反馈：

- 仍允许生成下周方案。
- UI 不要假装“根据你的反馈调整了”。

如果存在有效调整：

- 可用一个很轻量的说明告诉用户发生了什么，例如：
  - “这周几次因为没时间没执行，下周我把工作日晚餐换得更快一些。”
- 不使用责备、打分、达标率、连续天数等压力表达。
- 最多展示 1–2 条真正有用的调整原因，不做数据仪表盘。

### F. 自动测试最低要求

至少新增测试证明：

1. 没有反馈时，下一周正常生成且稳定。
2. 多次“没时间”后，下周工作日方案平均准备时间或复杂度有可验证下降。
3. 多次“太贵”后，在可行模板范围内下一周成本倾向下降。
4. “临时聚餐”不会错误触发全局惩罚。
5. “不喜欢”只降低相关日期餐食的再次出现，不修改永久 dislikedFoods。
6. 反馈调整不能绕过过敏/纯素/厨房能力等硬约束。
7. 本周与下周方案可同时保存和读取。
8. 本周与下周采购清单互不覆盖。
9. 旧版单周 storage 数据兼容读取或迁移。
10. 同一输入重复生成结果稳定。
