## 已确认需要修复的问题

1. 建档“你现在主要想做什么？”只能单选；应允许选择 1 个或多个目标，例如“减脂 + 改善健康”。
2. 采购清单使用“X 份餐食用量”，不是用户能直接购买的真实单位。
3. 首页把“早上/中午/晚上”和“早餐/午餐/晚餐”混成同一套导航，可能出现“午餐时间却仍高亮早上/早餐”等语义冲突。
4. 每周预算目前主要依赖模板中写死的 `estimatedCost`，例如某份外卖固定估价 11 元，并不知道用户当地真实价格。
5. 原产品设计明确要求的“个人食材环境模型”没有真正实现。`docs/PRODUCT.md` 已定义：记录用户生活范围内长期能买到什么、价格如何、是否稳定；MVP 原计划小票识别为主、货架拍摄为辅助。当前建档只收集概括性文字，无法形成真实价格/可得性数据。

## 当前产品边界

继续遵守 `AGENTS.md` 与 `docs/PRODUCT.md`：

- MVP 只做饮食管理。
- 不加入喝水、步数、久坐、运动打卡、训练计划等泛健康功能。
- 不做卡路里流水账，不做冰箱库存管理。
- 外卖、食堂、便利店、自己带饭、外食都是正常饮食环境。
- 避免考核式、责备式表达。
- 前五个大版本禁止加入吉祥物、卡通 IP、拟人角色。
- 本轮不接 Supabase、认证、真实 AI Provider、地图/MCP/外部 Agent。
- 本轮先恢复“真实数据可录入 + 可参与规划”的核心层；小票 OCR / 货架识别不作为本轮阻塞条件，避免为了识别技术再次拖延核心逻辑修复。

### Round 06：试用阻断问题修复 + 现实饮食数据层 v0

目标：只修 TRIAL-01 已确认的核心问题，让下一轮 7 天试用建立在可信的预算、采购和首页逻辑上。不要趁机扩产品范围。

Hermes 开始前必须：

1. 拉取最新 `main`。
2. 从最新 `main` 新建独立分支：`hermes/round-06`。
3. 禁止直接修改、commit、push 或 merge `main`。
4. 完成后创建 PR 指向 `main`，不得自行合并。

### A. 建档目标改为 1 个或多个

- “减脂 / 增肌 / 保持 / 改善健康”改为多选控件；至少选择 1 项。
- 数据层使用明确的数组语义，例如 `goals: Goal[]` 或等价结构。
- 必须兼容现有 localStorage 中只有单个 `goal` 的旧 profile：迁移为单元素数组，不能让现有用户打开后崩溃或资料丢失。
- 如果当前 planner 尚未真正使用 goal 做营养计算，不要伪造多目标营养逻辑；本轮只保证数据正确保存、显示和为后续营养层保留结构。

### B. 恢复“个人食材环境”最小可用数据录入

不要等待 OCR，先实现可用的手工录入，让系统第一次拥有用户自己的真实价格/可得性数据。

新增一个轻量入口，名称可使用“我的食材”或“常买食材”。不要做成冰箱库存。

至少支持两类数据：

1. **常买食材 / 便利店成品**
   - 名称
   - 真实购买数量
   - 真实单位：个 / 盒 / 杯 / 袋 / 瓶 / 克 / kg / 斤等
   - 一次购买价格
   - 常买地点或场景（可选）
   - 是否稳定能买到 / 常见程度（轻量枚举即可）

2. **外食 / 食堂 / 外卖的常见餐食价格**
   - 名称，例如“公司食堂一荤一素”“楼下牛肉粉”“常点鸡肉饭”
   - 场景：公司食堂 / 外卖 / 外食 / 便利店
   - 每份实际价格
   - 是否稳定可得

要求：

- 本轮存储继续使用 localStorage，不引入账号或云数据库。
- 不要求复杂商品库、条码库或库存数量。
- 可以新增最小的数据类型与 storage API，例如 `FoodEnvironmentItem[]`；具体命名可调整。
- 当前已有 `food_environment_items` 的 Supabase 草稿结构可以参考概念，但本轮不要接 Supabase。
- 建档第 3 步应明确引导用户：完成基础建档后，可以补充“常买食物/常见外食的实际价格”，让预算更贴近现实。
- 如果用户暂时不录入，产品仍能工作，但必须明确预算只是参考估算，不能伪装成精确本地价格。

### C. 预算逻辑改为“用户数据优先 + 未知价格降级”

当前模板写死 `estimatedCost` 可以保留为 fallback，但其语义必须降级为“参考估价”。

预算计算优先级：

1. 能匹配到用户个人食材环境中的真实价格 → 使用用户价格。
2. 无用户价格 → 使用模板参考估价，但把该餐/该周标记为包含估算价格。

要求：

- 不得声称系统知道用户当地真实价格，除非实际来自用户录入。
- 周方案应能够区分：预算“基于用户价格”还是“包含参考估价”。
- 如果本周存在未知/参考价格，预算提示采用类似“本周约 ¥X，其中部分为参考估价”的诚实表达。
- 对外食模板，不要仅凭原料价格推算一份外卖价格；优先匹配用户录入的对应餐食/场景价格。
- 如果无法精准匹配具体外卖，可使用用户录入的同场景平均/常见价格（若实现了该结构）；否则继续用参考估价并明确标注。
- 预算减价/替换仍可复用现有 planner，不要另造第二套规划器。
- 过敏、禁忌、厨房能力、准备时间等硬约束优先级不得被价格逻辑绕过。

### D. 采购清单改为真实可买数量

当前 `shoppingItems: string[]` + “X 份餐食用量”必须升级为结构化采购需求。

每个需要用户采购的餐食模板应提供可聚合的真实份量，例如：

- 鸡蛋：2 个
- 鸡胸肉：150 g
- 无糖酸奶：1 杯
- 玉米：1 根
- 米：80 g（或使用统一、可理解的购买单位）

具体合理份量由当前模板定义，不要求本轮达到专业营养处方精度，但必须能形成实际采购数量。

聚合后采购页显示真实单位，例如：

- 鸡蛋 8 个
- 鸡胸肉 600 g
- 无糖酸奶 4 杯

要求：

- 食堂 / 外卖 / 外食由商家提供的原料仍不得进入家庭采购清单。
- 便利店成品属于真实采购，可以进入清单。
- 同名同单位可合并；单位不兼容时不要硬加。
- 下周方案更新时，仍要保留“项目仍存在则保留已买状态；消失移除；新增未买”的既有规则。
- 采购项稳定标识不要依赖数组排序 index，避免数量/排序变化导致已买状态无故丢失。

### E. 首页重新收敛为“接下来怎么吃”

不要继续把“时间段”和“餐别”做成混合 tab。

首页主逻辑改为：**根据真实本地时间 + 当天实际存在的餐食，告诉用户下一顿是什么。**

要求：

- 当前时间已过早餐但未到午餐 → 主卡聚焦午餐。
- 用户“通常不吃早餐” → 早上也可以直接显示下一顿午餐，不出现早餐缺失/早餐 tab 高亮冲突。
- 午餐后 → 聚焦晚餐。
- 晚餐后 → 不再假装还有“下一顿晚餐”，可显示当天反馈入口 + 明天最必要的轻量预览。
- 可以保留“稍后”预览，但它必须从主逻辑自然派生，而不是再造一套早上/中午/晚上选中状态。
- 周计划页继续承担按日期/餐别浏览职责；首页不必重复成为完整日程浏览器。
- 任何时候 UI 中“现在是什么时间”“下一顿是什么”不得互相矛盾。

### F. 试用版本兼容与数据迁移

- Round 05 已经存在用户 localStorage 数据。

- 如果某类旧数据无法可靠迁移，要给用户明确、最小的重新生成入口，而不是静默错算。
