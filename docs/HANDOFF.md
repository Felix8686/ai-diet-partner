## ChatGPT 本轮复验结论

Round 04 主体方向正确，CI 通过，但 **PR #4 暂不合并**。目前发现 2 个合并前问题，只修这两项，不扩大 Round 04 范围。

### 1. 下周页面会把下周一错误标记成“今天”

`app/week/page.tsx` 当前在查看下周时把：

`todayIndex = 0`

随后又用 `safeSelected === todayIndex` 判断是否显示“今天”。

结果是：用户切到“下周”，默认选中的下周一会在标题和无障碍标签中被写成“今天”，即使今天实际上仍在本周。

要求：

- “今天”只能用于真实设备本地日期所在的当前周日期。
- 查看下周时，所有日期都应显示真实日期，不得把下周一称为“今天”。
- 默认选中下周一可以保留，但它只是下周一，不是今天。
- 增加回归测试，至少覆盖：本周真实今天仍正确标记；下周默认第一天不出现“今天”。

### 2. 下周方案一旦提前生成，后续新增反馈永远不会再进入下周调整

当前 `/week` 的行为是：

- 只要 `plans.next` 已存在，本周页面就只显示“查看下周方案”。
- `generateNextWeek()` 不再有入口重新根据本周后来新增的反馈更新下周方案。

因此用户如果周二就点了“看看下周怎么调整”，系统只会读取周一/周二已有反馈；之后周三到周日的新反馈不会再影响已保存的下周方案。

这会破坏 Round 04 的核心承诺：**本周执行失败原因应真实影响下一周方案。**

要求使用最小、明确的 v0 修正，不做复杂历史/版本系统：

- 下周方案已经存在时，用户仍必须有办法“根据本周最新反馈更新下周方案”。
- 不要要求用户清 localStorage 或重新建档。
- 更新时重新读取当前周全部反馈，再调用现有 planner；不得另造第二套规划逻辑。
- 如果本周反馈没有新增有效调整，不要制造虚假的“已调整”文案。
- 重新生成下周方案时，不能错误覆盖本周方案或本周采购状态。
- 对已经存在的下周采购勾选状态要采取明确、安全的行为：
  - 优先保留仍然存在于新采购清单中的已买状态（可按稳定名称/标识匹配）；
  - 已从新方案消失的项目自然移除；
  - 新增项目默认为未买。
- UI 文案保持轻量，例如已有下周方案后提供“根据最新反馈更新”入口即可，不做复杂版本管理。

自动测试至少证明：

1. 先用一部分反馈生成下周方案；
2. 再新增本周反馈；
3. 更新下周方案后，新反馈真实进入调整结果；
4. 本周方案与本周采购状态未被覆盖；
5. 下周原有采购项中仍存在的项目，其已买状态可保留；新出现项目默认未买；
6. 相同 profile + 相同最新反馈 + 相同 nextWeekStart 重复更新结果稳定。
