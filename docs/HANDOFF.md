## 当前产品边界

继续严格遵守 `AGENTS.md` 与 `docs/PRODUCT.md`：

- 当前 MVP 只做饮食管理。
- 前五个大版本禁止加入吉祥物 / 卡通 IP / 拟人角色。
- 不加入喝水、步数、久坐、运动打卡、训练计划等泛健康功能。
- 不做卡路里流水账。

- 外卖、食堂、便利店、外食属于正常饮食环境。

- 未经明确任务不得扩展地图、美团/高德、MCP、外部 Agent、真实 AI Provider 等能力。

## 已知问题 / 技术债

- 当前周方案仍来自固定 mock 餐单，用户建档并不会真正改变生成结果。
- 当前采购清单仍是固定 mock 数据，没有从周方案反推。
- 采购勾选刷新后会丢失。
- profile / plan / shopping / feedback 的 localStorage 访问分散在页面中，缺乏统一数据层。
- 尚未接入 Supabase、认证、真实 AI Provider、预算计算和个人食材环境模型。
- 当前 `lint` 实际为 TypeScript `tsc --noEmit`，尚未配置 ESLint。

## 已做出的产品决策

- 下一阶段仍然**不接 Supabase、不接真实 AI Provider**。
- 先验证最核心的一件事：**用户建档资料是否能真实改变一周饮食方案。**
- 下一阶段允许使用本地确定性规则和有限餐食模板来实现个性化规划，不追求 AI 文案或复杂营养算法。
- 这一轮的重点不是增加页面，而是让现有闭环从“能点”升级为“数据真的贯通”。

## 下一阶段任务

### Round 03：本地个性化规划引擎 v0

Hermes 收到任务后必须：

1. 从最新 `main` 拉取代码。
2. 新建独立分支：`hermes/round-03`。
3. 禁止直接 commit / push / 修改 `main`。
4. 完成后创建 PR 指向 `main`，不得自行合并。

### A. 建立统一的本地数据层

不要再让各页面直接散落调用 localStorage。

建立简单、清晰、可替换的数据访问层，例如放在：

- `lib/storage/`
- 或等价的轻量目录

至少统一管理：

- 用户建档资料
- 当前周方案
- 当前周采购清单及已买状态
- 每日反馈

要求：

- key 命名集中管理。
- JSON 解析失败时有安全回退，不让页面崩溃。
- 保留以后替换成 Supabase repository 的可能性，但不要现在过度抽象。

### B. 把固定周餐单改造成“餐食模板池”

不要直接继续扩充 `weekPlan` 硬编码结果。

建立有限但结构化的餐食模板数据，每个模板至少能表达：

- 早餐 / 午餐 / 晚餐 / 可选加餐
- 食物/菜品名称
- 使用场景：家里 / 食堂 / 外卖 / 便利店等
- 准备时间
- 所需厨房能力，例如炒、煮、微波等
- 粗略单份成本
- 主要食材 / 标签
- 可替换方案

模板数量只要足以验证规则，不要为了“内容丰富”大量堆菜谱。

### C. 实现确定性的 `generateWeekPlan(profile, week)`

核心要求：用户资料必须真实影响结果。

生成规则至少覆盖：

1. **厨房条件**
   - 用户没有某种厨房能力，就不能生成必须依赖它的餐食。

2. **做饭时间**
   - 工作日餐食不得超过用户填写的最大可接受制作时间。
   - 如果用户选择“通常不做饭”，优先使用食堂 / 外卖 / 便利店 / 无需烹饪方案。

3. **外食环境**
   - 用户填写公司食堂、外卖、便利店等场景后，工作日方案应该体现这些现实条件。

4. **喜欢 / 讨厌 / 禁忌**
   - 明确讨厌或禁忌的食物不能出现在主方案中。
   - MVP 可以使用简单标签 / 文本匹配，不需要 NLP 系统。

5. **预算**
   - 根据模板中的粗略成本估算一周费用。
   - 用户填写了周预算时，方案应尽量不超过预算。
   - 如果现有模板无法满足预算，必须返回明确的“规则无法满足”状态供 UI 使用，禁止偷偷超预算。
   - 不要在 UI 中用责备语气显示预算问题。

6. **重复度**
   - 避免同一个主餐方案连续大量重复。
   - 不要求绝对不重复；现实可执行性优先于菜谱丰富度。

7. **稳定性**
   - 同一个用户、同一周在没有资料变化时刷新页面，方案不能随机改变。
   - 可以用周 key + 稳定排序/简单 seed，避免纯 `Math.random()`。

### D. 打通真实本地闭环

三步建档完成后：

1. 保存 profile。
2. 使用 profile 生成该用户当前周方案。
3. 保存周方案。
4. 从周方案涉及的主要食材生成当前周采购清单。
5. 跳转 `/week`。

随后：

- 首页读取已保存的当前周方案，不再直接读取固定 mock `weekPlan`。
- `/week` 读取已保存方案。
- `/shopping` 读取由当前周方案派生的采购清单。
- 采购“已买 / 未买”状态刷新页面后必须保持。
- 如果用户还没有 profile / plan，页面必须有合理的空状态或引导回建档，不能报错。

### E. 反馈暂时只做到“数据可被下一轮使用”

这一轮不要实现复杂的自动周调整。

要求：

- 已保存的反馈可以通过统一数据层按日期读取。
- 为下一阶段的“根据执行失败原因调整下一周”留出清晰的数据接口。
- 不要提前加入 AI Provider。

### F. 验收测试

必须新增自动测试证明“建档真的改变方案”。至少覆盖：

1. 一个“工作日很忙、10 分钟以内、公司食堂/外卖、厨房能力少”的 profile。
2. 一个“愿意做 30–60 分钟、厨房条件较完整、主要在家吃”的 profile。
3. 两个 profile 生成的方案应有可验证的差异。
4. 缺少某厨房能力时，不得选中依赖该能力的模板。
5. 讨厌 / 禁忌食物不得进入方案。
6. 周预算存在时，生成结果不得静默超过预算。
7. 同一用户同一周重复生成结果保持稳定。
8. 采购清单从周方案生成，勾选后刷新仍保持状态。

完成后执行：

- `npm run lint`
- `npm test`
- `npm run build`
- 本地浏览器 smoke test：建档 → 生成方案 → 首页 → 周方案 → 采购勾选 → 刷新检查持久化 → 每日反馈

### G. 本轮明确禁止

不要接入：

- Supabase
- 用户认证
- 真实 AI / LLM Provider
- 地图 / 高德 / 美团
- MCP / 外部 Agent
- 小票 OCR / 货架识别
- 完整营养数据库
- 新的泛健康功能
- 吉祥物

不要为了这一轮重做视觉风格；只修复因为真实数据流产生的必要 UI 状态。
