### 1. 采购清单把食堂 / 外卖 / 外食的“原材料”也算成用户要购买的食材

当前 `deriveShoppingList(plan)` 会无差别遍历所有餐食的 `ingredients`。

这会导致例如：

- 周一午餐 = 公司食堂“鱼 + 青菜 + 米饭”
- 周二午餐 = 外卖鸡肉饭

采购清单仍要求用户购买鱼、青菜、米饭、鸡肉等原材料。

这与产品最重要的现实场景原则冲突：用户在食堂或点外卖时，不应该为了这顿饭购买原材料。

要求：

- 采购清单必须区分“用户需要自己采购的东西”和“由食堂/餐厅/外卖提供的食物”。
- `公司食堂`、`外卖`、`外食`餐食不得把其原材料加入家庭采购清单。
- `便利店`属于用户实际购买场景，可以加入用户需要买的成品，例如茶叶蛋、玉米、无糖豆浆、即食鸡胸等，但不要把它们错误拆成无需单独购买的内部原料。
- 最好给模板增加一个很轻量的结构化字段，例如 `shoppingItems` / `procurementMode` 或等价方案，而不是继续只靠 `ingredients` 猜测；不要做大型库存系统。
- 增加自动测试：以“工作日食堂/外卖为主”的 profile 生成方案后，采购清单不能出现这些外食餐食的原材料；便利店需要购买的成品仍可出现。

### 2. 晚餐无可行模板时，晚间每日反馈入口会一起消失

当前首页 evening 分支把“晚餐卡片”和“每日反馈入口”放在同一个 `dinner ? ... : MissingMeal` 条件里。

因此如果严格禁忌/条件导致当天晚餐没有可行模板，用户只能看到“晚餐暂时没有合适模板”，却无法提交当天反馈。

每日反馈是核心闭环的一部分，不应依赖晚餐是否生成成功。

要求：

- 晚间每日反馈入口必须独立于 `dinner` 是否存在。
- 有晚餐：显示晚餐 + 反馈入口。
- 无晚餐：显示轻量缺失提示 + 反馈入口。
- 增加回归测试或浏览器 smoke 场景证明“无晚餐时仍可进入每日反馈”。

### 3. `weekdayWeekendDifference` 目前没有真正参与规划，周末总是被无条件放宽

当前 `canUseTemplate()` 在 `isWeekend` 时直接返回 `true`（厨房能力过滤之后），因此会跳过工作日准备时间和“通常不做饭”等限制；而建档中的 `weekdayWeekendDifference` 没有用于规划。

结果是：用户即使选择“每天时间差不多”或“周末反而更忙”，周末仍可能突然被安排 30 分钟的家庭烹饪餐。

要求采用简单、确定性的 v0 规则即可：

- `工作日更忙，周末有时间`：周末允许比工作日更宽松，可安排较长家庭烹饪。
- `每天时间差不多`：周末继续遵守用户填写的做饭时间上限，不要自动放宽。
- `周末反而更忙`：周末不得比工作日更复杂；优先同等或更快、更省事的方案。
- “通常不做饭”的行为必须与上述周末差异规则形成明确、可测试的一致逻辑，不得因为进入周末就完全失效。
- 增加至少 2 个测试，证明“每天时间差不多”和“周末反而更忙”不会在周末突然出现超出约束的复杂餐食。

- 当前规划引擎仍是有限本地模板池和确定性规则，不是真实 AI，也没有完整营养计算。

- profile、周方案、采购清单和每日反馈仍只存在当前浏览器，尚未跨设备同步。
- 重新完成建档会生成新方案并重置当前周采购清单，尚未支持历史周方案。
- 当前 `lint` 实际为 TypeScript `tsc --noEmit`，尚未配置 ESLint。
